# ChainTree Hierarchical Bit Map DSL

**ChainTree Hierarchical Bit Map DSL** is a lightweight, "zero-copy" engine for managing hierarchical system state in embedded systems. It allows you to define a tree of devices (Robots, Conveyors, Sensors) and automatically propagates bit-level logic (like Alarms, Safety Interlocks, or Ready States) up the hierarchy in real-time.

It separates **Definition** (Lua DSL) from **Runtime** (C99), generating highly optimized, read-only data structures that require no string parsing on the embedded target.

---

## 1. The Problem

In industrial automation, state is hierarchical:

* If a **Joint** has an error, the **Robot** is faulted.
* If the **Robot** is faulted, the **Work Cell** is red.
* If the **Work Cell** is red, the **Production Line** stops.

Hardcoding this logic (`if robot.fault || conveyor.fault ...`) is brittle. ChainTree Hierarchical Bit Map DSL solves this by defining **Bitspaces** with merge rules.

---

## 2. DSL Tutorial

The system is defined using a Lua-based Domain Specific Language (DSL). Create a file named `schema.lua`.

### Step A: Define "Bitspaces" (The Channels)

Bitspaces are parallel layers of logic that run through your entire tree. You define *how* they merge parent and child states.

```lua
local D = require("dsl_runtime")

return D.Schema{
  name = "FactoryDemo",
  
  bitspaces = {
    -- If ANY child has an Alarm, the Parent has an Alarm.
    D.Bitspace{ name="ALARM", merge="OR" },
    
    -- If ALL children are Ready, the Parent is Ready.
    D.Bitspace{ name="READY", merge="AND" },
    
    -- Determining state priority (e.g. Fault > Warning > Idle)
    D.Bitspace{ name="STATE", merge="PRIORITY" }
  },

```

### Step B: Define "Classes" (The Hardware)

Define the memory layout for your devices. You allocate "Banks" of memory for specific bitspaces.

```lua
  classes = {
    D.DeviceClass{
      name = "RobotArm",
      -- This device needs 128 bits (16 bytes) for Alarms
      banks = { ALARM=128, READY=32 },
      
      -- Give names to specific bits (optional, for documentation/export)
      bits = {
        ALARM = { 
          { name="OverTorque", idx=0 },
          { name="CommLost",   idx=1 } 
        }
      }
    }
  },

```

### Step C: Define the Tree (The Topology)

Instantiate your classes into a hierarchy using dot-notation paths. The engine infers the parent/child relationships from the path strings.

```lua
  nodes = {
    -- The Root is "Plant"
    D.Node{ path="Plant.Line1.CellA.Robot1", class="RobotArm" },
    D.Node{ path="Plant.Line1.CellA.Conv1",  class="Conveyor" },
  },

```

### Step D: Static Configuration (The Data)

You can also attach static configuration data (Integers, Floats, Strings). The generator will hash the paths so they take up zero string storage in C.

```lua
  config = {
    Plant = {
      Line1 = {
        Config = { Speed = 500, SafetyEnabled = true }
      }
    }
  }
}

```

## 3. The Build Process

The `codegen.lua` script compiles your Schema into C source code.

### Prerequisites

* **LuaJIT** (Recommended) or Lua 5.1+
* **dkjson** (Lua library for JSON output)

### Generating Code

Run the generator:

```bash
luajit codegen.lua

```

### Output Files

1. **`generated_FactoryDemo.h`**: A tiny header exposing the **Descriptor**.
```c
extern const chain_desc_t FactoryDemo_desc;

```


2. **`generated_FactoryDemo.c`**: The implementation containing all static arrays (Layouts, Rules, Offsets). All symbols are `static` to prevent namespace pollution.
3. **`config_sidecar.json`**: A JSON file containing the full config tree, useful for Linux gateways or UIs to read the map.

---

## 4. C Runtime Architecture

The C runtime is generic. It doesn't know about "Robots" or "Factories". It operates purely on the **Descriptor** produced by the generator.

### Core Components

* **`chain_tree.h/c`**: Manages memory (Arenas) and Lookup (Hashing).
* **`chain_tree_logic.c`**: Implements the "Bubble Up" recursion logic.
* **`chain_desc_t` (ROM)**: The static blueprint generated by Lua.
* **`chain_tree_t` (RAM)**: The runtime instance holding the dynamic bit state.

### Usage Example

```c
#include "chain_tree.h"
#include "generated_FactoryDemo.h"

int main() {
    // 1. Initialize the Tree
    chain_tree_t tree;
    // Pass the generated descriptor to the generic runtime
    chain_tree_init(&tree, &FactoryDemo_desc, NULL);

    // 2. Set an Alarm on a deep child node
    // The engine automatically finds the node and its parents
    int ALARM_BANK = 0;
    chain_set_bit(&tree, ALARM_BANK, 0, true, "Plant.Line1.CellA.Robot1");

    // 3. Verify Logic Propagation
    // Check if the "Plant" (Root) is now alarmed?
    uint8_t* plant_alarms = chain_get_bits(&tree, ALARM_BANK, "Plant");
    
    if (*plant_alarms & 0x01) {
        printf("CRITICAL: Plant is stopped due to Robot error!\n");
    }

    chain_tree_destroy(&tree);
    return 0;
}

```

## 5. Technical Highlights

### Printf-Style Bit Position Lookup

A key feature of the ChainTree Hierarchical Bit Map DSL is its ability to resolve hierarchical paths without allocating memory for strings. The runtime includes a zero-copy path walker that accepts `printf`-style format specifiers.

This allows you to access dynamic array structures in your hierarchy (e.g., iterating over lines or cells) efficiently.

**How it works:**
The function `hash_vprintf` incrementally calculates the FNV-1a hash of the path as it processes the format string and arguments.

```c
// Example: Accessing bits in a loop without string buffers
for (int line = 1; line <= 5; line++) {
    for (int cell = 1; cell <= 10; cell++) {
        
        // No sprintf() buffer needed!
        // Hashes "Plant.Line1.Cell1.Robot1" directly on the fly
        uint8_t* bits = chain_get_bits(&tree, 0, 
            "Plant.Line%d.Cell%d.Robot1", 
            line, cell
        );
        
        if (bits) {
            // ... process bits ...
        }
    }
}

```

This approach enables O(log n) lookups using binary search on the pre-computed hash table, while maintaining human-readable path definitions in your code.

### Contiguous "Arena" Memory

Memory is not fragmented by thousands of `malloc` calls for every node.

* The generator calculates the exact total size needed for the `ALARM` bitspace across the *entire* tree.
* The runtime performs **one** allocation for the `ALARM` arena.
* Nodes just point to offsets within that block.

### Multi-Schema Support

Because the generated data is encapsulated in a `chain_desc_t` and hidden behind `static` variables, you can link multiple different system definitions (e.g., `RobotA_desc`, `RobotB_desc`) into the same binary without collision.
