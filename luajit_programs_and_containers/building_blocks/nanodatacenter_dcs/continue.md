### Architecture locked in today

See memory file `project_nanodatacenter_dcs_decisions.md` for full detail. Short
version:

**Blackboard vs per-KB dicts**
- ChainTree blackboard stays scalar-only, may be empty.
- Per-KB Lua global dicts (`system_control_globals`, `node_control_globals`) for
  strings, config, connection handles.
- Cross-KB `process_globals` dict for intra-process supervision.
- Single ChainTree VM = no concurrency.

**Provisioning**
- Two-step: vault_init (one-time) + provision_all (per change). But today we
  pivoted secrets: no vault, no encryption, no ciphertext in repo.
- Language: LuaJIT (avoid nested library hell). FFI to libcrypto is available if
  we ever need it.
- Secrets live only on operator's laptop at
  `~/.config/nanodatacenter/secrets.env` (mode 600, not git-tracked).
  Provisioning scripts `source` it, or fail loudly if env missing.
- `provisioning.json` (non-secret config, site-wide) mounted at
  `/etc/nanodatacenter/provisioning.json` on each CPU.
- Env vars: `MASTER_FLAG`, `CPU_ID`, `PG_PASSWORD`, `NATS_PASSWORD`, `MQTT_PASSWORD`.

**KB structure (dcs.lua)**
- Single DSL file; test order = KB index. KB 0 = system_control, KB 1 = node_control.
- system_control launch: READ_ENVIRONS → READ_PROVISIONING_JSON →
  KILL_ALL_CONTAINERS → SET_SYSTEM_STATE → outer static SM (master/slave).
- Master and slave branches each have inner SM: sync / setup / monitor / teardown.
- Master *starts* infra containers; slave *verifies* them.
- Master *creates* shared `system.*` KV keys + runs an aggregator waiting on all
  nodes' `containers_operational` before flipping `system.ready`.
- Slave *reads* shared keys read-only; creates its own `node.<cpu_id>.*` keys.
- node_control KB: single SM (sync/setup/monitor/teardown), same code on every
  CPU, differs only by assigned container list.

**Readiness (two-phase)**
- Phase 1 per-CPU: `node.<cpu_id>.containers_operational` — containers up, apps idle.
- Phase 2 site-wide: `system.ready` — master aggregates all, flips gate.
- Apps subscribe directly to NATS KV `system.ready` (no relay).
- system_control mirrors `system.ready` to `process_globals.system_ready_current`
  for node_control's visibility.
- Container lifecycle tied to teardown only, not to `system.ready` transitions.

**Policy**
- **No retry.** Any verify failure = `terminate_system`; docker restart takes
  over. Only voluntary loop is teardown → sync.
- **No quorum.** Single node stale → whole-site teardown. Consistent, harsh.
- **No runtime master failover.** Master hardware failure = tier-1 (provisioning)
  concern.

**Error oneshot vocabulary**
- `ERR_INFRA_FAIL`, `ERR_NODE_CTRL_START_FAIL`, `ERR_AGGREGATOR_TIMEOUT`,
  `ERR_CONTAINERS_START_FAIL` → `terminate_system`.
- `ERR_MONITOR_TRIP`, `ERR_CONTAINER_DIED`, `ERR_TEARDOWN_REQUESTED` →
  `change_state(sm, "teardown")`.
- `ERR_TEARDOWN_FORCE` → force-kill, proceed.

**Logging scope**
- Exceptions + short resource usage stream only. No general-purpose logging.
- Tools identified in repo: `nats/StreamBuffer` (persistent circular KV) +
  Welford's algorithm (incremental mean/variance, 3 scalars, Chan's merge).
- Destination declared per-stream in the KB DSL (not per-call).
- TimescaleDB deferred.

**Base container / process controller**
- Every app container derives from a common base with LuaJIT + process controller
  + baked sqlite KB (generated by provisioning DSL at image build).
- Controller scope: startup / shutdown / one-for-one supervision. Not a broker
  proxy — children open their own pg/nats/mqtt clients.
- Controller ↔ child signaling: stdin line protocol (`"READY\n"` / `"IDLE\n"`).
- App languages: primarily LuaJIT, occasional Python, rare C.

## Session 1 (2026-04-09) — original plan (preserved)

First planning session for the multi-CPU distributed control system
("nanodatacenter DCS") that will subsume the existing single-CPU planner
architecture. We scoped the problem, analyzed the current KB + planner
code, and agreed on a three-tier model. We stopped partway through
defining system control.

### The problem we are solving

The current construct DSL (`knowledge_base/{postgres,sqlite3}/construct_kb/`)
and `ros_planner_ii` assume **one CPU**:

- One DB file = one CPU.
- One ltree namespace = one process.
- No placement annotations on nodes, VNs, RPC servers, etc.
- No cross-CPU transport binding in the schema.
- `check_installation()` reconciles the entire satellite set into one DB.
- `master_build.lua` emits a single build artifact.

Today's runtime glues processes together with NATS+MQTT at runtime, but
the DSL itself does not know the distributed system exists. We need a
model where the DSL and the runtime both acknowledge multiple CPUs.

### The three-tier model

**Tier 1 — Provisioning level.** Installer / bootstrapper. Not part of the
running system. Ansible-style setup scripts (now LuaJIT, per session 2).
Runs once; re-runs when containers update or a new KB loads. Responsible for
installing Docker containers on each CPU, loading the Postgres knowledge base
(where the construct DSL runs), setting per-CPU identity env var on every
processor, and setting a master-flag env var on exactly one CPU. Hands off
to system control.

**Tier 2 — System control level.** The head. One per site. The CPU whose
master flag is set. Implemented as a ChainTree behavior tree. Same binary as
node control; the entry point reads the master env var and dispatches to
system_control. (Session 2 refined this: entry is the outer static SM inside
the system_control KB; dispatch is by master_flag.)

**Tier 3 — Node control level.** One per non-master CPU. Same binary as system
control; dispatched to node_control when the master flag is not set.
(Session 2 refined this: node_control is a separate KB supervised by
system_control, not a dispatch branch.)

### Architectural invariants established session 1

- **Single binary, env-dispatched.** Every CPU runs the same image. The entry
  point reads env, then branches.
- **ChainTree BT as the implementation language** for both system control
  and node control.
- **Env vars are the identity mechanism.** CPU id and master flag are baked
  in at provisioning time. Runtime never negotiates, elects, or discovers.
- **Postgres KB lives on the master.** Built at provisioning, queried at
  runtime. How edge CPUs get their local KB slice (SQLite) is an open
  question — mostly resolved in session 2: all CPUs read pg directly, no
  per-CPU SQLite slice needed.
- **Robot instances do NOT live in the KB.** Only robot classes. Instances
  are runtime state, discovered via registration.

### Carry-forward context

- Both Postgres and SQLite have parallel `construct_kb/` (build-time) and
  `data_structures/` (runtime) directories.
- Runtime facades (`kb_data_structures.lua`) are ~95% surface-compatible
  across backends; notable gap is Postgres-only `document_table`.
- The `database` parameter in `CDT.new()` is a schema base name.
- Satellite table labels are reserved: `KB_STATUS_FIELD`, `KB_STREAM_FIELD`,
  `KB_JOB_QUEUE`, `KB_RPC_SERVER_FIELD`, `KB_RPC_CLIENT_FIELD`,
  `KB_JSONB_FIELD`, `KB_BIT_MASK`.
- `ros_planner_ii` opens SQLite read-only at runtime (`upload_flag = true`).
  Runtime fast path is NATS KV + MQTT, not satellite tables.
- Existing infrastructure to reuse (all on `planner-net`): `pg-vector`,
  `nats-js-ram`, `mosquitto-ram-ws_main`, `kv-bridge`, `openresty-gateway`,
  orchestrator image.
