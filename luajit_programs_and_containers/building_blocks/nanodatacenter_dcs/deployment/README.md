# deployment/

**GENERATED per-CPU deployment artifacts. Git-ignored.**

Contents of this directory (except this README + `.gitignore`) are
regenerated by:

1. `../construction/slice_bootstrap.sh` — writes
   `<cpu>/bootstrap.db` (read-only sqlite with identity + assignments).
2. `../construction/stage_deploy.sh --mode=<dev|prod>` — wires in
   the runtime tree and seeds `<cpu>/env.sh` if it doesn't exist.

## Per-CPU layout (example: `cpu_01/`)

```
deployment/cpu_01/
├── start.sh       Watchdog wrapper; execs runtime/dcs_host/dcs.lua.
├── env.sh         PG_HOST, POSTGRES_PASSWORD, PG_USER, etc.
│                  OPERATOR-OWNED after first stage. Not clobbered.
├── bootstrap.db   Read-only. Regenerated each slice_bootstrap run.
└── runtime/       Symlink (--mode=dev) or copy (--mode=prod) of ../../runtime/.
```

## What the operator does

**Once, on first stage:**
- Open `<cpu>/env.sh` and fill in passwords / hostnames.

**Routinely:**
- `./start.sh` from inside the CPU's directory.

**Never:**
- Edit `bootstrap.db`, `start.sh`, or `runtime/*`. They will be
  clobbered on the next build.

## Dual-mode rationale

- `--mode=dev` symlinks runtime → source tree. Edits to `../runtime/`
  show up immediately on restart. Used on the laptop during
  development.
- `--mode=prod` copies runtime as a tree. Self-contained, survives
  source-tree relocation. Used when baking an image or shipping to
  a real CPU.
